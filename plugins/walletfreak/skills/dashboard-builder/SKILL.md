# Dashboard builder

Resolve this plugin root from this skill's installed path. Start its local workspace with `python3 <plugin>/scripts/local.py start` if necessary. Travel is a configurable itinerary overview with one saved-trip selector; research and trip files stay with the selected trip. Actions shows user follow-ups. The wallet editor and statement uploads stay in their respective workspaces. Requests and analysis remain in the conversation.

1. Read `local.py status`, `local.py catalog` and `local.py layout`. Status describes saved trips; catalog/layout contain design metadata. Reuse existing results and read the saved wallet only when it is relevant to the requested work. Never replace it with sample data.
2. For a request to generate an itinerary dashboard, establish destinations, travelers, dates and flexibility from the conversation and existing trip. Ask only for missing information needed for research. Use travel-plan/provider-research to research, Credit Cards' wallet-optimizer when installed for payment cards and planned versus used benefits, and stay-route-map for stay dates and route order. Never invent quotes or booked status to fill a template.
3. Publish the trip using trip-board before configuring its layout. An existing usable trip can be reused. For finance analysis, use walletfreak-spending:spending-analysis only when the user asks to analyze references. A template alone cannot create findings. State missing data clearly instead of presenting an empty layout as completed research.
4. Choose a Travel template or edit the current Travel layout, preserving unrelated saved data. Travel layouts use only `travel.*` sources; full wallet and spending views stay in their own workspaces. Home lists saved trips; Travel has a local trip selector: `travel.itinerary` and `travel.actions` show one saved trip, never concatenated trips. For multiple trips, return the intended trip title so the user can select it. Themes are paper, sage, midnight and editorial; density is compact or comfortable. Do not invent component IDs or add trip IDs/private data to layout JSON.
5. Save JSON with `expected_revision` from the read and `layout`, then run `local.py layout --input <request.json>` (or `--input -`). On a revision conflict, reread and reconcile; never blindly overwrite newer edits.
6. Verify the published trip has itinerary rows and linked payment details, then verify the saved layout sources match the requested output. Open the private local viewer when browser tools are available; check the intended trip, map/list fallback and narrow viewport. If only CLI validation is available, say so. Return the private workspace link and trip title, not a terminal dump of financial data. Do not claim visual verification without viewing it.

The authoritative v1 contract is [layout schema](../../assets/components/v1/layout.schema.json); the [bundled catalog](../../assets/components/v1/catalog.json) includes complete templates. A layout contains only version, title, theme, density and blocks; every block contains a unique id, component, source and title. No URLs, scripts, custom HTML/CSS, filesystem paths, credentials or financial values belong in a layout. Sources are named local bindings such as wallet.programs or spending.metrics. Templates never upload or analyze source documents.

The public component gallery and catalog are published with the website at /components.html and /components/v1/catalog.json. A read-only catalog MCP service can expose list_components, get_component, list_templates, get_template and get_layout_schema when deployed. Its inputs are public component/template IDs only. Never send a user layout, wallet, statement or metric values to the public service. A newer catalog may contain components unsupported by this installation: validate against the local catalog and upgrade the plugin explicitly if needed. The bundled catalog and renderer work offline.

For empty spending metrics, use the installed spending-analysis workflow when the user asks for analysis; adding a metrics component alone does not authorize reading statements. Travel findings come from trip-board and wallet fields come from the local wallet. Keep separate currencies and reported dates intact. The Travel overview shows at most 100 rows per component and directs users to the full views for more.

Use `wallet-cards` with `wallet.cards` for linked card tiles; keep `data-table` for spreadsheet layouts. The itinerary component includes a compact timeline and optional stay/route fields. Existing v1 layouts remain supported.

The `concierge-travel` template uses `trip-brief`, `action-queue` and `itinerary`. The brief draws a schematic route from verified location coordinates; the action queue derives next steps from the selected trip. Home and the public template gallery share the same warm shell, while the gallery uses fictional examples.
