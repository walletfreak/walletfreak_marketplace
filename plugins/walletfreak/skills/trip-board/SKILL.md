# Trips and personal wallet

The browser is a results viewer and personal wallet, not an agent interface. Trip intake, research requests, clarifications and sign-in coordination belong in the host conversation. There is no request queue, chat, Research button or account-connect workflow in the dashboard. Use [travel-plan](../travel-plan/SKILL.md) for new research; rendering supplied findings needs no account access.

Resolve the plugin root from this installed skill. Run `python3 <plugin>/scripts/local.py start` and return its private local link. The access key is private; the loopback link works only on the machine running the server. Opening the viewer does not trigger research or a wallet balance prompt. Always run start again before sharing a viewer link, especially after a plugin update; it replaces a server from an older installation without deleting saved data. Use the newly printed link because a restart changes its access key. If start fails, report the error instead of returning a cached link.

## Publish results from the conversation

1. Read the [example](assets/example-trip.json) and [data contract](references/data.md). Produce sanitized findings for the requested trip. For hotel listings, include the optional `image` object from the data contract when an official photo is available; retain its source link and describe the photo accurately. Include itinerary entries linked to flight, hotel, transport or lounge option IDs, plus dated activities. State local time zones in schedule text and preserve input order. Display the proposed itinerary immediately without requiring users to select options first. For every purchase, include its payment card, reason and benefit-usage ledger as defined in the data contract. Show planned, used, not-used, conditional or unavailable; used requires dated evidence or a dated user report. Missing card details stay To confirm, and selections never spend benefits.
2. Run `local.py publish --input <private-json-file>` or `--input -` with `{"findings": {...}}`. It saves a new result and returns its id/revision. This command only publishes data; it does not start research. Start the viewer with `local.py start --view travel --trip <returned-id> --review comparison` when sharing a comparison, or `--review research` for the option list, and return that fresh private link with a concise recommendation. A plain Travel link is for the itinerary overview.
3. To refresh an existing result, run `local.py status`, then publish `{"id":"<id>","expected_revision":<revision>,"findings":{...}}`. Full snapshots must retain selected/shortlisted options; mark stale options appropriately. Concurrent edits or deleted results reject the update. Never recreate deleted results unless the user asks to create a new result.
4. Use only sanitized display data: no owner identities, account balances, credentials, account/card numbers, confirmation codes or private URLs. Public HTTPS source links are required; query strings/fragments are stripped, but remove sensitive path segments and free text yourself. Publishing results does not authorize copying the personal wallet into an export.

All research stays in the active conversation. Closing the host does not start background work. The viewer keeps existing results available while its local server runs; it cannot send work to the agent or refresh inventory. Publish `actions` only for a concrete step the traveler must take, such as signing in or deciding on a specific verified term. Unknown prices, credit balances, expiry dates and blocked research belong in gaps or uncertainty, not Actions. Booking actions appear only for available proposals with complete costs; empty hotel nights remain visible in the calendar. The Actions view lets the traveler mark explicit steps addressed. Booking status changes only through reviewed itinerary data.

## Personal wallet

The Wallet tab lets users add/edit/remove cards, loyalty programs, approximate points/miles, status, owner aliases, preservation preferences, gift cards, TravelBank/stored funds, airline credits, certificates, upgrades, companion awards, lounge visits and reporting/expiry dates. It opens with card and rewards tiles, linked accounts and credits; Table view provides bulk editing with search and keyboard navigation. Cards link to rewards accounts by stable IDs; balances live on programs and must not be duplicated or summed per card. Legacy wallets are backed up locally before a v2 migration; deleting the wallet also deletes this migration backup. Saving explicitly stores their entries locally. Blank balances/dates remain unknown; never automatically date facts, infer a live balance or deduct proposed spending. Follow `traveler-profile` for optional reuse and one balance check per planning session. `local.py wallet` reads the saved wallet without starting the server; use only when relevant to the user's request. `status` omits wallet contents.

The Load existing wallet action imports a supported legacy traveler-profile.md only into an empty wallet and leaves the original unchanged. Sign-ins saves device-encrypted local JSON separately from wallet.json and initializes automatically on first use. Users fill this form themselves; use `wallet-sync` for requested portal login and balance updates. Never read raw credentials. Plugins & skills provides a lightweight read-only local skill browser.

## Keep or delete

Results are in `~/.walletfreak/local/results.json`; the separate wallet is `~/.walletfreak/local/wallet.json` (or the dedicated WALLETFREAK_DATA directory). Delete these results removes only the displayed result. Delete personal wallet removes only wallet.json. Files are private local plain text, not an encrypted vault. Manually deleting results.json clears results on the next refresh without affecting wallet.json. Downloaded files and prior conversation history are independent copies.

Download trip file exports standalone HTML containing the research itinerary, saved shortlist and comparison selections/subtotals, never the wallet. Users may keep or delete that file later; it works without the server; optional remote hotel photos require internet access. For an explicitly requested standalone board, run `python3 <this-skill>/scripts/render_board.py <sanitized-trip.json> <output>/index.html`; existing output requires intentional --overwrite. Offline filters/shortlists are temporary. Public hosting needs a separate user request. The fictional example is only for development or a requested demo.

Check option counts, filters, evidence links, itinerary components, costs, dates/time zones and unresolved gaps. Available means at observation, never guaranteed now. No booking, polling or automatic balance changes.

Use [stay-route-map](../stay-route-map/SKILL.md) when adding hotel locations and routes. Keep critical gaps visible; payment reasoning and evidence expand on demand.

For reviewed confirmation imports, itinerary entries may carry a `price` string directly even without a linked research option. Treat it as a reported booking total or potential price; do not silently add it to verified research subtotals.
